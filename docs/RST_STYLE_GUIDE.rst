RST 写作规范
=============

适用范围
--------

本规范适用于仓库中的题目正文和项目说明。目标是让 RST 源文件本身清晰可读，不依赖 Sphinx 或其他构建工具。

文件与标题
----------

* 一道题对应一个 RST 文件。
* 文件名格式为 ``0001-two-sum.rst``。
* 题目文件按每 100 题一个目录存放。
* 顶级标题使用等号，下一级使用短横线，再下一级使用波浪线。
* 标题装饰线长度应覆盖标题文本，不使用混乱的层级符号。

推荐标题层级：

.. code-block:: rst

   0001. Two Sum
   =============

   问题抽象
   --------

   解法一：哈希表
   --------------

   Python
   ~~~~~~

段落与列表
----------

* 普通段落之间保留一个空行。
* 无序列表使用 ``*``。
* 有序步骤使用 ``#.``，避免手工维护序号。
* 只在确实存在并列关系时使用列表。
* 不用大量短句列表代替完整解释。

代码块
------

代码使用 ``.. code-block::``，并指定语言：

.. code-block:: rst

   .. code-block:: python

      for value in values:
          print(value)

指令后的正文必须缩进三个空格。代码本身再保持语言需要的缩进。

代码注释遵守教学预算：

* 首次出现的重要语法可以完整解释；
* 已强化过的知识只保留一句提醒；
* 熟悉内容不再重复解释；
* 算法关键状态、不变量和容易误写的地方可以持续注释；
* 禁止逐行翻译代码。

行内代码
--------

标识符、表达式、复杂度和文件路径使用双反引号：

* ``unordered_map``
* ``left <= right``
* ``O(n)``
* ``state/PROGRESS.toml``

外部链接
--------

使用标准 RST 链接：

.. code-block:: rst

   `LeetCode 1 <https://leetcode.com/problems/two-sum/>`_

仓库内部关联也使用普通相对链接，不使用依赖 Sphinx 的 ``:doc:`` 角色：

.. code-block:: rst

   `0001. Two Sum <../0001-0100/0001-two-sum.rst>`_

说明与警告
----------

只有确实需要突出边界时才使用指令：

.. code-block:: rst

   .. note::

      这里补充不会打断主线的信息。

   .. warning::

      这里说明会导致错误的关键边界。

不要把普通段落全部包装成 ``note`` 或 ``warning``。

表格
----

简单对比优先使用 ``.. list-table::``，复杂内容优先改写成列表或段落。不要为了视觉效果制造难维护的网格表格。

.. code-block:: rst

   .. list-table::
      :header-rows: 1

      * - 方法
        - 时间复杂度
        - 空间复杂度
      * - 哈希表
        - ``O(n)``
        - ``O(n)``

数学表达
--------

简单表达式使用行内代码即可。只有推导确实需要数学排版时才使用 ``.. math::``。算法题正文应优先让读者理解状态与推理，避免无必要的公式化。

单题内容取舍
------------

题目模板提供可选结构，不是强制目录。判断规则如下：

* 简单题删除没有内容的“证明”“第二解法”等章节；
* 复杂题补充状态定义、不变量、证明、反例或状态表；
* 只保留有教学差异的多种解法；
* 只解释当前读者真正需要的语言知识；
* 每题都应保留复杂度、易错边界和最小自检。

提交前检查
----------

#. 题号、标题、文件名和原题链接一致。
#. 题目重述为原创表达。
#. 标题层级连续，指令缩进正确。
#. 所有代码块都标明语言。
#. 多语言代码实现同一算法语义。
#. 复杂度与代码一致。
#. 注释密度符合知识账本状态。
#. 内部相对链接指向真实文件。
#. ``state/PROGRESS.toml`` 与 ``state/CONCEPT_LEDGER.toml`` 已同步更新。
