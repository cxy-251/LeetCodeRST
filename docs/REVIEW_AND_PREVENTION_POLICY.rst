RST 审查与防复发规则
=====================

目的
----

本规则用于审查已经完成的题目，并把发现转化为后续题解的公共约束。审查的首要目标不是
统一措辞或批量润色历史文件，而是：

* 发现会影响正确性、可运行性或教学结论的确定性缺陷；
* 找出会在后续题目中重复出现的系统性风险；
* 把系统性风险固化到模板、质量门和语言规则中；
* 只在确有必要时修改已经完成的题目。

审查结果分流
------------

每项发现必须先归入以下类别，再决定修改范围。

A 类：公共规则问题
~~~~~~~~~~~~~~~~~~

包括结构、解释密度、注释风格、证明组织、检查顺序、常见语言风险提醒不足等问题。
这类发现默认只修改公共文件，例如：

* ``docs/PROBLEM_TEMPLATE.rst``；
* ``docs/AUTOMATION_QUALITY_GATE.rst``；
* ``docs/SOLUTION_AND_TYPES_POLICY.rst``；
* ``docs/RST_STYLE_GUIDE.rst``；
* ``state/CONCEPT_LEDGER.toml`` 的知识分类规则。

不得仅为统一风格、补充更多解释、调整标题或增加示例而批量回改历史题目。

B 类：确定性缺陷
~~~~~~~~~~~~~~~~

以下问题必须修复对应题目文件，同时更新公共规则防止复发：

* 算法会返回错误结果、漏解、重复答案或不能终止；
* 代码无法编译、存在确定性运行错误或越界访问；
* C 存在未定义行为、错误容量、所有权或释放契约；
* Rust 存在无法通过借用检查、错误所有权转移或接口不匹配；
* R 存在 ``<-`` / ``<<-`` 作用域错误、错误引用语义或危险下标序列；
* Julia 存在一基索引错误、递减范围误用或原地接口语义错误；
* TypeScript / JavaScript 因位运算 32 位转换、整数精度或 ``undefined`` 判断产生错误；
* 复杂度结论与代码明确不一致；
* 正确性证明依赖不成立的前提，或讲解与代码使用不同算法；
* 题意、接口、返回格式或输入约束被明确写错。

修复 PR 只修改缺陷题目、严格必要的状态文件和对应公共规则，不推进 ``next_problem``。

C 类：证据不足
~~~~~~~~~~~~~~

无法确认题意、运行环境缺少、语言实现只能静态检查或怀疑存在问题但尚未构造反例时：

* 不得宣称存在确定性错误；
* 不得宣称运行或编译通过；
* 记录验证范围和缺失证据；
* 必要时加入 ``needs_revision``；
* 在证据补齐前不扩大修改范围。

审查维度
--------

逐题审查至少覆盖：

#. 题意、接口、自建示例和关键约束是否一致；
#. 主算法是否满足题目约束，核心不变量是否真实成立；
#. 正确性依据是否证明合法性、完整性、无重复和终止性中实际需要的部分；
#. 时间复杂度、额外空间、递归栈、结果空间和输出复制成本是否区分清楚；
#. 十种语言是否实现同一个算法语义，而不是机械直译；
#. 辅助函数、导入、平台类型、返回结构和内存责任是否完整；
#. 数值、索引、字符单位、作用域、所有权、可变性和标准库 API 边界是否正确；
#. RST 标题、指令、缩进、链接、代码块和知识账本是否一致。

验证证据等级
------------

审查结论必须明确证据等级：

``运行验证``
   已在当前环境执行测试，并说明覆盖的正常、边界、随机或对拍用例。

``编译验证``
   已用对应编译器或类型检查器通过，必要时启用严格警告；编译通过不等于算法正确。

``静态验证``
   只检查接口、语法结构、索引、作用域、所有权或逻辑，不能写成“运行通过”。

``基准对拍``
   与独立、明显正确的基准实现比较；基准不能复用被测代码的核心逻辑。

高风险语言检查
--------------

C
~

* 分配容量必须由题目上界或动态增长规则证明；
* 返回二维数组时检查外层容量、每行容量、``returnSize`` 和 ``returnColumnSizes``；
* 明确输入是否被修改、谁释放返回内存、失败路径是否泄漏；
* 无符号长度相减、整数提升、空指针和零长度分配必须单独检查。

Rust
~~~~

* 检查所有权转移、``clone`` 的必要性、可变借用生命周期和 ``Option`` 处理；
* 不能用伪代码式接口掩盖无法通过借用检查的实现；
* 平台签名与辅助函数的所有权约定必须一致。

TypeScript / JavaScript
~~~~~~~~~~~~~~~~~~~~~~~

* 位运算会把 ``number`` 转为 32 位有符号整数；涉及 ``2^31`` 边界时优先使用算术取模和除法；
* 检查 ``Map.get`` 的 ``undefined`` 与合法零值；
* 超过安全整数范围时不能假装 ``number`` 保持精确；
* 类型检查应使用严格模式，运行验证和类型验证分别记录。

Julia
~~~~~

* 明确题目零基算法坐标与 Julia 一基数组位置的转换；
* ``a:b`` 在 ``a > b`` 时可能产生递减范围，空区间应使用显式守卫或安全迭代器；
* ``!`` 命名、原地修改、返回值和方阵/向量类型约束必须与题目接口一致；
* 检查整数除法、取模和切片是否改变算法语义。

R
~

* ``<-`` 修改当前调用环境，``<<-`` 搜索父环境；递归层局部选择变量不得误用 ``<<-``；
* 需要跨递归共享可变状态时优先使用显式 ``environment``，并区分共享状态和当前层局部变量；
* 避免用 ``1:n`` 表达可能为空的序列，优先使用 ``seq_len``、``seq_along`` 或显式守卫；
* R 的值语义、写时复制和一基索引必须在原地题接口中说明。

复杂度与证明检查
----------------

* 复杂度必须定义变量含义；
* 枚举、组合、排列和字符串构造题要计入输出数量与复制成本；
* 区分算法额外空间、递归栈和返回结果空间；
* 平均、摊还和最坏复杂度不得混写；
* 正确性依据不能只复述循环，需要说明为什么排除安全、状态充分、答案不漏不重；
* 使用贪心时必须说明局部选择为何不损失最优解；使用回溯时必须说明搜索空间覆盖和去重规则。

审查批次与 Git 规则
-------------------

* 审查期间不生成新题，不推进 ``next_problem``；
* 一次可以审查连续若干题，但每题结论独立记录；
* 只有 A 类发现时，提交公共规则升级，不批量改历史 RST；
* 出现 B 类缺陷时，创建独立 ``fix:`` PR，修改最小必要范围；
* 同一个根因在多题中造成确定性错误时，可以在同一修复 PR 中修改受影响题目，但必须逐题列出证据；
* 审查状态保存在 ``state/PROGRESS.toml`` 的 ``[review]`` 区域；
* 未完成的审查不能伪装成题目已经重新验证。

防复发闭环
----------

每个被确认的根因至少落实到一个公共检查项：

#. 在模板中增加写作或验证提示；
#. 在质量门中增加完成判定；
#. 在语言规则中增加语义边界；
#. 在知识账本中登记需要持续提醒的高风险概念；
#. 后续出现同类题时执行针对性测试或静态检查。

公共规则升级只约束后续内容和未来修订，不自动触发 0001 至 0050 的风格回填。
