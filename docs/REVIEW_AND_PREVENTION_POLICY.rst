0001–0050 逐题审查与后续防复发规则
================================

目的
----

本阶段逐题读取 ``0001`` 至 ``0050`` 的 RST 正文，从真实内容中提炼 ``0051`` 至
``0100`` 的优化规则。

审查不是为了重新发布或统一润色前 50 题。默认不修改任何历史题目文件；发现的问题只记录为
审查样本，并转化为后续模板、质量门、语言边界和验证要求。只有用户以后明确指定某一道历史题
需要修改时，才处理该题。

证据来源
--------

审查结论必须来自以下一手内容：

#. 对应题目的完整 RST 正文；
#. 正文中的题意、示例、证明、复杂度和易错点；
#. 十种语言的实际代码块；
#. 与该题直接相关的知识账本条目和公共规则。

以下信息不能代替内容审查：

* PR 标题、PR 描述和评论；
* 提交信息、合并状态和文件行数；
* 自动任务的完成报告；
* 先前对话中没有重新核对正文的结论。

这些信息只能帮助定位文件或确认流程，不能证明题解内容正确、完整或具有教学质量。

审查顺序与状态
--------------

* 严格按题号从 ``0001`` 审查到 ``0050``；
* 每题必须完整读取，不能只抽取标题、开头或代码片段；
* 每题结论写入 ``state/REVIEW_0001_0050.toml``；
* 跨题规则写入 ``docs/REVIEW_FINDINGS_0001_0050.rst``；
* ``state/PROGRESS.toml`` 的 ``review.current`` 指向下一道尚未审查的题；
* 审查完成前保留 ``next_problem = 51``，但禁止生成 0051；
* 审查完成后再把项目恢复为正常题目批次。

历史文件边界
------------

本阶段只获取优化方法，不回改 ``0001`` 至 ``0050``：

* 不修正文案、标题、示例、证明或复杂度；
* 不修复旧代码块；
* 不建立针对旧题的 ``fix:`` PR；
* 不因规则升级批量格式化历史 RST；
* 即使发现确定性问题，也只记录现象、风险和前向规则；
* 用户以后明确指定修改某道题时，再单独处理。

逐题审查维度
------------

每道题至少检查以下内容，并记录“没有发现”“单题观察”或“规则候选”。

题意与约束
~~~~~~~~~~

* 输入、输出、结果顺序和是否允许修改输入是否明确；
* 数值范围、长度下界、字符集合和平台类型是否足以支撑代码假设；
* 自建示例是否真正覆盖主算法；
* 边界示例是否能区分正确与错误实现。

算法与证明
~~~~~~~~~~

* 主解法是否与正文描述一致；
* 核心状态或不变量是否明确；
* 指针移动、候选排除、剪枝和贪心选择是否有安全性依据；
* 二分查找是否证明搜索方向、候选区间和终止性；
* 回溯是否证明覆盖、去重和终止；
* 正确性依据是否只是复述代码步骤。

复杂度
~~~~~~

* 是否定义 ``n``、``m``、``k``、``U`` 等变量；
* 是否区分最坏、平均和摊还复杂度；
* 是否区分算法额外空间、递归栈和返回结果空间；
* 哈希表是否区分期望与最坏情况；
* 切片、字符串转换、``collect``、``strsplit``、``[]byte``、复制结果路径等隐藏成本
  是否计入；
* 十种语言因值语义、所有权或字符表示产生的复杂度差异是否单独说明。

十语言实现
~~~~~~~~~~

* 十种语言是否实现相同算法语义；
* 必要导入、辅助函数、平台类型和版本前提是否明确；
* 输入是否被消费、排序、交换或原地修改是否说明；
* C 的容量、失败路径、释放责任和返回所有权是否安全；
* Rust 的借用、移动、``take``、``clone`` 和 ``Option`` 是否真实可行；
* Go 的字符串转换、切片共享和版本相关 API 是否明确；
* TypeScript 的 32 位位运算、``number`` 精度和 ``undefined`` 是否安全；
* Julia 的一基索引、空区间、递减范围和切片副本是否安全；
* R 的一基索引、空序列、写时复制、``<-`` / ``<<-`` 和 ``environment`` 是否安全；
* 失败或不可达路径是否会返回一个看似合法的普通答案。

RST 与教学结构
~~~~~~~~~~~~~~

* 标题、指令、缩进、链接和代码块语言是否清楚；
* 解释是否靠近对应代码；
* 简单题是否重复大量模板内容；
* 困难题是否缺失必要证明、状态表或反例；
* 自检问题是否验证核心理解，而不是复述定义。

发现分层
--------

单题观察
~~~~~~~~

只在某一道题出现、尚不能证明会重复的问题。记录在该题条目中，不立即提升为公共规则。

跨题模式
~~~~~~~~

在至少两道题中出现相同根因，或者一次出现就属于高风险语言语义、内存、所有权或复杂度问题。
这类模式进入 ``docs/REVIEW_FINDINGS_0001_0050.rst``。

前向规则
~~~~~~~~

跨题模式必须转换为 ``0051`` 以后可执行的检查项，至少落入以下一个位置：

* ``docs/PROBLEM_TEMPLATE.rst``；
* ``docs/AUTOMATION_QUALITY_GATE.rst``；
* ``docs/SOLUTION_AND_TYPES_POLICY.rst``；
* ``docs/RST_STYLE_GUIDE.rst``；
* ``docs/REVIEW_FINDINGS_0001_0050.rst``；
* 自动任务的读取清单和验证提示。

规则必须描述“以后具体检查什么”，不能只写“注意边界”或“提高质量”。

首批已确认前向方向
------------------

从 ``0001`` 至 ``0005`` 的正文中已经确认以下方向，详细证据见
``docs/REVIEW_FINDINGS_0001_0050.rst``：

* 字符串题必须把精确字符约束与字节、代码单元、码点或字形簇模型绑定；
* 复杂度必须计入语言特有的字符串转换和输入复制；
* C 分配失败和不可达路径不能返回看似正常的部分答案或默认值；
* 二分查找证明必须覆盖搜索方向与排除安全性；
* 代码块必须包含必要导入，或明确说明由平台预置；
* 使用版本相关标准库 API 时必须声明版本，或改用仓库可控的兼容写法；
* 哈希解法必须区分期望复杂度与最坏复杂度。

完成条件
--------

只有满足以下条件，才算完成 ``0001`` 至 ``0050`` 的规则提取审查：

#. 50 个 RST 均已完整读取；
#. ``state/REVIEW_0001_0050.toml`` 中 50 道题均为 ``reviewed``；
#. 每项跨题模式都能追溯到具体题目正文；
#. 公共规则已经转化为 0051 以后可执行的检查项；
#. 没有修改任何历史题目 RST；
#. ``state/PROGRESS.toml`` 恢复 ``next_batch.status = "ready"`` 后，才允许生成 0051。
