逐题审查证据与历史题处理规则
============================

当前状态
--------

``0001`` 至 ``0050`` 的第一次逐题审查已经完成。``0051`` 至 ``0100`` 正在执行第二轮逐题审查，
当前已覆盖 ``0051`` 至 ``0055``。

审查目的
--------

每轮逐题审查完成三件事：

#. 从真实 RST 和十语言代码中识别正向样本、确定性问题与验证限制；
#. 把可复用模式整理为带来源的前向质量规则；
#. 保留结构化证据和事实更正，方便后续追溯与独立修复。

审查证据
--------

内容结论来自：

* 对应题目的完整 RST；
* 题意、示例、算法状态、证明和复杂度；
* 十语言代码块；
* 与该题直接相关的仓库约定；
* 必要时使用目标语言官方文档核对语义。

PR 描述、提交信息、合并状态和对话报告只说明工作发生过，不证明题解质量。

记录分层
--------

单题观察
~~~~~~~~

只描述某一道题的具体表现。它可以是正向样本、确定性错误、语言差异或验证限制。

跨题模式
~~~~~~~~

多个题目出现相同根因，或单次出现就属于高风险内存、所有权、索引、数值、作用域或语言语义问题时，
形成跨题模式。

前向规则
~~~~~~~~

跨题模式只有转换为明确检查动作后，才进入批次 ``rules``。第二轮全部完成后，再把稳定规则归并为下一
阶段的完整执行规则。模糊描述如“注意边界”不构成规则。

冲突处理
--------

批次记录是审查快照，可能保留后来被更正的观察。出现冲突时：

#. 先读取 ``state/PROGRESS.toml``；
#. 再读取 ``state/REVIEW_INDEX.toml`` 的 ``corrections``；
#. 执行对应阶段已经完成归并的前向规则；
#. 批次记录和详细发现只用于追溯证据来源。

历史题边界
----------

被审查题目正文默认保持原样。审查发现不会自动触发回改，即使已经确认确定性问题。

用户明确指定某一道历史题需要修复时：

#. 重新读取该题完整 RST、审查记录和相关规则；
#. 明确缺陷属于算法、编译、运行、复杂度、接口、内存、所有权还是文档；
#. 只修改该题和确实受影响的公共文件；
#. 使用针对性运行或静态验证；
#. 形成独立原子提交，题号完成进度保持不变。

语言语义验证
------------

闭包赋值、范围构造、无符号算术、写时复制、所有权与平台位运算等语言特定路径，不能由其他语言的
运行结果替代。缺少目标运行时时，只能标记静态未验证；高风险路径应使用官方文档和最小可执行测试。

后续维护
--------

每个第二轮五题批次：

#. 完整读取五题正文和十语言代码；
#. 新增结构化记录与详细证据；
#. 更新 ``REVIEW_INDEX``、``PROGRESS`` 和资料目录；
#. 不修改历史题目正文；
#. 以一个原子提交更新 ``main``。
