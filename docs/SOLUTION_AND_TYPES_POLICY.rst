解法选择、标准库与基础类型规则
==============================

多种解法如何取舍
----------------

一道题可能存在暴力、排序、哈希、双指针、动态规划、数学推导等多种方法。本项目不按“能找到多少种方法”衡量质量，而按教学差异决定是否保留。

主解法
~~~~~~

每道题选择一个主解法。主解法应在正确性、复杂度、可读性和通用性之间取得最好平衡。

主解法默认提供 10 种核心语言的完整实现：C、C++、Python、Java、Rust、Go、TypeScript、C#、Julia、R。

主解法必须讲清：

* 问题抽象；
* 核心状态或不变量；
* 为什么成立；
* 时间与空间复杂度；
* 关键边界；
* 语言实现中的必要差异。

十种语言必须实现同一个算法语义。允许为了语言安全、接口和所有权采用不同的数据表示，
不允许某种语言悄悄换成更弱、不同复杂度或无法证明等价的实现。

对照解法
~~~~~~~~

第二种及后续解法只在下列情况保留：

* 时间或空间复杂度发生实质变化；
* 使用了不同的数据结构或状态表示；
* 展示了重要的算法演进，例如暴力到哈希、递归到动态规划；
* 能解释主解法为什么更优；
* 某种语言存在真正不同的惯用实现。

对照解法不要求机械重复 10 种语言。通常只给算法说明、伪代码，或选择 1 至 2 种最能体现差异的语言。只有两种方法都属于本题核心学习目标时，才为两种方法都提供完整多语言实现。

低价值变体
~~~~~~~~~~

以下内容通常不单独列为新解法：

* 只改变量名或循环方向；
* 同一算法在容器 API 上的小变化；
* 复杂度、状态和证明完全相同的写法；
* 为增加数量而加入的递归或函数式改写；
* 只把一种语言逐字翻译成另一种语言。

已有轮子如何处理
----------------

标准库容器与算法属于编程语言能力的一部分。只要题目允许，应优先使用可靠、常见的标准库轮子，例如哈希表、集合、队列、双端队列、堆、排序和二分查找。

标准库写法
~~~~~~~~~~

当一个标准库函数或容器能够自然解决问题时，应展示这种工程写法，并在代码注释中说明：

* API 的语义；
* 关键复杂度；
* 当前使用依赖的前提；
* 容易误解的边界。

不能把调用 API 的代码当作无需解释的黑盒，也不能为了“显得底层”而拒绝使用标准库。

轮子隐藏核心算法时
~~~~~~~~~~~~~~~~~~

如果一个现成函数几乎完全隐藏了本题要求学习的算法，例如直接调用排序、全排列、二分查找或字符串匹配函数，则采用双轨表达：

#. ``工程写法``：展示实际开发中可以使用的标准库方案；
#. ``教学写法``：实现本题真正需要理解的算法过程。

工程写法可以很短。教学写法承担主要解释和多语言实现。

需要手写轮子的情况
~~~~~~~~~~~~~~~~~~

只有下列情况手写基础结构或算法：

* 题目本身要求实现该结构或算法；
* 标准库改变了题目的复杂度、语义或约束；
* 当前知识点就是该轮子的内部机制；
* 目标语言没有合适的标准库支持；
* 为解释关键不变量必须暴露内部状态。

不得在每道 BFS 题中重新实现通用队列，也不得在每道堆题中重新实现完整堆。使用轮子和理解轮子是两个独立教学目标。

基础类型复用
------------

平台提供的类型
~~~~~~~~~~~~~~

LeetCode 通常会为链表、树和部分图题提供 ``ListNode``、``TreeNode``、``Node`` 等基础类型。题目代码默认使用平台提供的定义，不在每种语言、每道题中重复声明。

首次遇到某种基础类型时：

* 在题目中简短说明字段与引用关系；
* 在 Mermaid 图中展示节点与指针结构；
* 在代码块中用一条注释标明“由平台提供”；
* 将类型约定登记到 ``state/CONCEPT_LEDGER.toml``。

后续题目直接使用该类型。只有字段结构不同、可变性不同或语言表示发生变化时再次解释。

Julia 与 R
~~~~~~~~~~

Julia 和 R 不依赖 LeetCode 平台类型。项目为它们维护统一的仓库级节点表示：

* Julia 使用 ``mutable struct`` 表达需要原地修改的链表和树节点；
* R 使用 ``environment`` 表达需要引用语义的可变节点；
* 首次出现时给出完整定义并解释；
* 后续题目复用同一约定，不重复讲解所有字段和语法；
* 当题目需要不同节点结构时，在该题局部定义并说明差异。

队列、栈、双端队列与堆
~~~~~~~~~~~~~~~~~~~~~~

这些结构默认使用各语言的标准库或惯用容器：

* C++ 使用 STL 容器；
* Python 使用 ``list``、``deque``、``heapq`` 等；
* Java、C#、Go、Rust、TypeScript 使用各自常见容器；
* Julia 和 R 使用适合当前规模与语义的惯用表示；
* C 根据题目约束使用最小的局部数组或共享辅助约定。

仅当题目目标是实现栈、队列、堆或双端队列时，才完整手写其内部结构。

题目专属辅助类型
~~~~~~~~~~~~~~~~

``TrieNode``、并查集、线段树节点、状态对象等若属于当前算法核心，应在当前题目中定义。若只是通用基础设施，应复用已有约定，不重复展开。

代码独立性
----------

题目代码以 LeetCode 可提交接口或等价独立函数为目标。为保持教学聚焦，可以省略平台已经提供的基础类型定义，但不能省略影响算法理解的状态、辅助函数或题目专属结构。

当代码依赖仓库级基础类型约定时，题目正文必须明确指出对应类型与引用语义，不能让读者猜测。

每种语言还必须明确：

* 必要的标准库导入；
* 输入是否会被排序、交换或原地修改；
* 返回结果的顺序是否有要求；
* 辅助函数、比较器、哈希键和状态对象是否完整；
* 内存、资源或返回对象由谁持有和释放；
* 平台接口与正文描述是否一致。

跨语言高风险边界
----------------

C
~

* 动态数组容量必须由题目上界证明，或实现可检查的增长策略；
* 二维结果检查外层指针容量、每行容量、``returnSize`` 和 ``returnColumnSizes``；
* 所有分配、失败路径、临时缓冲区和返回所有权必须说明；
* 无符号长度相减前先判断大小，避免下溢；
* ``INT_MIN`` 取绝对值、乘法和下标换算前根据需要扩宽；
* 比较器避免直接相减造成溢出；
* 零长度输入、空指针和 ``malloc(0)`` 的使用不能依赖未说明行为。

C++
~~~

* 区分有符号下标与 ``size_t``，避免比较和相减错误；
* 迭代器失效、引用生命周期、移动后对象和比较器严格弱序必须检查；
* 标准库算法复杂度和前提要与正文一致；
* 输入原地排序或修改时必须明确。

Python
~~~~~~

* 检查可变对象共享、浅拷贝、默认可变参数和闭包变量；
* 切片会复制，复杂度不能忽略；
* 大整数不会溢出，但不能因此掩盖其他语言的固定宽度边界；
* 递归深度可能成为实现限制，必要时选择迭代写法。

Java 与 C#
~~~~~~~~~~

* 中间运算必须在运算前提升到更宽类型；结果赋给宽类型并不会修复已经发生的溢出；
* 检查装箱、集合键相等语义、数组与列表接口差异；
* 递归、整数除法、取模和字符单位必须与算法假设一致；
* 返回集合是否暴露可变内部状态需要明确。

Rust
~~~~

* 代码必须能通过真实借用检查，不能用伪代码式可变别名；
* 检查 ``take``、``clone``、移动、切片借用和递归调用之间的所有权关系；
* ``Option`` / ``Result`` 不能用不可达假设随意 ``unwrap``；
* 平台函数签名、整数转换和下标类型必须一致；
* 为绕过所有权而复制整个结构时，需要说明复杂度代价。

Go
~~

* 切片复制只复制描述符，保存结果时检查是否共享同一底层数组；
* ``append`` 可能复用或重新分配底层数组，不能依赖隐含别名；
* 字符串按字节还是按 Unicode 码点遍历必须与题目约束一致；
* ``int`` 宽度、整数转换和映射零值需要明确。

TypeScript / JavaScript
~~~~~~~~~~~~~~~~~~~~~~~

* ``number`` 是双精度浮点数，超过安全整数范围后不能保持精确整数语义；
* 位运算会强制转换为 32 位有符号整数，涉及 ``2^31`` 边界时使用算术取模和除法；
* ``Map.get`` 返回 ``undefined``，不能用真假值判断合法的 ``0``；
* 数组复制、排序原地修改和字符串代码单元语义需要说明；
* 使用 ``--strict`` 做类型检查，类型通过和运行通过分开记录。

Julia
~~~~~

* 题目零基算法坐标转换到 Julia 一基位置时逐个检查；
* ``a:b`` 在 ``a > b`` 时可能形成递减范围，空循环需要显式守卫或安全迭代器；
* 原地函数使用 ``!``，并明确是否返回 ``nothing`` 或修改后的对象；
* 切片通常分配副本，``view`` 与普通切片语义不同；
* 整数除法、取模、矩阵维度和抽象数组类型不能机械照搬其他语言。

R
~

* ``<-`` 修改当前调用环境，``<<-`` 搜索父环境；当前递归层的局部选择变量不得使用 ``<<-``；
* 跨递归共享可变状态优先放入显式 ``environment``，共享状态与局部变量必须分开；
* 可能为空的迭代禁止使用 ``1:n``，优先使用 ``seq_len``、``seq_along`` 或显式守卫；
* 一基索引、向量回收规则、值语义和写时复制必须检查；
* 原地题通常需要返回修改后的对象，正文不能假装调用者对象必然被原地改变。

复杂度与结果空间
----------------

复杂度描述必须与代码一致：

* 定义所有变量含义；
* 区分最坏、平均和摊还复杂度；
* 将排序、哈希、重复扫描、字符串拼接和标准库调用计入时间；
* 区分算法额外空间、递归栈和返回结果空间；
* 排列、组合、枚举、分组和字符串构造题必须计入输出数量与复制成本；
* 语言为了所有权或值语义产生的额外复制，若改变渐进复杂度或实际内存模型，需要单独说明。

审查与修复边界
--------------

历史题目的审查遵守 ``docs/REVIEW_AND_PREVENTION_POLICY.rst``：

* 风格、结构、解释密度和检查流程问题只升级公共规则，不批量回填旧题；
* 确定性的算法、编译、运行、复杂度、接口、内存、所有权、作用域和索引错误必须修复对应题目；
* 证据不足时记录验证限制，不能把静态判断包装成运行结论。
