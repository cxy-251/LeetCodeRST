对话驱动执行流程
================

文件定位
--------

本文件保留原路径 ``AUTOMATION_DIRECT_MAIN_POLICY.rst``，用于兼容现有 README、状态记录和交接说明。
实际执行方式已经统一为：用户在对话中发起工作，助手在当前回复周期内完成，并把完整结果写入
``main``。

执行入口
--------

LeetCode 题解生成、逐题审查、规则提炼和缺陷修复都从用户的明确消息开始。

仓库文件承担跨对话共享状态：

* ``state/PROGRESS.toml`` 记录当前阶段和下一步；
* ``state/REVIEW_INDEX.toml`` 记录逐题审查位置；
* ``state/CONCEPT_LEDGER.toml`` 记录知识进度；
* README、规则文件和题目 RST 共同构成当前工作上下文。

标准工作流
----------

每轮工作按以下顺序执行：

#. **读取最新状态**

   从最新 ``main`` 读取 ``AGENTS.md``、根 README、当前阶段规则、状态文件以及本轮直接相关的题目。

#. **确定本轮范围**

   根据用户指令和状态文件确定审查范围、生成题号或修复对象。范围在写入前固定，并在当前回复中
   完成。

#. **准备完整结果**

   一次性准备本轮涉及的正文、代码、审查记录、前向规则、索引、README 和状态更新。所有文件使用
   同一份阶段判断和题号范围。

#. **执行质量检查**

   对照 ``docs/AUTOMATION_QUALITY_GATE.rst``、
   ``docs/FORWARD_RULES_0051_0100.rst`` 以及当前阶段规则，检查正文、证明、复杂度、十语言实现、
   文件路径和状态一致性。

#. **提交到 main**

   将本轮完整结果形成一个可理解的原子提交，直接更新 ``main``。提交说明写清工作类型、题号范围和
   状态变化。

#. **复查提交结果**

   重新读取 ``main`` 中的目标文件，确认题号、审查进度、README、规则和状态账本保持一致。

#. **报告并结束本轮**

   在当前对话中报告实际完成内容、主要发现、提交结果和下一步。下一轮从用户新的消息开始。

逐题审查流程
------------

当 ``phase = "review_extracting_rules"`` 时：

#. 从 ``state/REVIEW_INDEX.toml`` 的 ``review.current`` 开始；
#. 按用户指定范围审查，未指定时默认连续五题；
#. 完整读取每道题的正文、证明、复杂度和十语言代码；
#. 将单题观察写入 ``state/reviews/NNNN-NNNN.toml``；
#. 将详细证据写入 ``docs/review-findings/NNNN-NNNN.rst``；
#. 把稳定的跨题模式提升到 ``docs/FORWARD_RULES_0051_0100.rst``；
#. 同步 ``REVIEW_INDEX.toml``、``PROGRESS.toml`` 和两个 README；
#. 当前历史范围保持原样，审查结论用于改进后续题目；
#. 复查 ``review.current``、``reviewed_count`` 和下一审查范围。

新题生成流程
------------

当规则提炼完成并进入题解生成阶段时：

#. 从 ``state/PROGRESS.toml`` 的 ``next_problem`` 开始；
#. 根据难度预算确定连续题号范围；
#. 为每道题完成原创重述、示例、算法选择、正确性证明、复杂度和十语言实现；
#. 将前期审查提炼出的规则应用到实际代码和正文；
#. 同步题目 RST、范围 README、根 README、``PROGRESS.toml`` 和
   ``CONCEPT_LEDGER.toml``；
#. 完成验证后形成一个原子提交写入 ``main``；
#. 复查完成范围和新的 ``next_problem``。

缺陷修复流程
------------

用户指定修复某道题时：

#. 读取该题完整 RST、相关公共规则和当前状态；
#. 明确缺陷属于代码、证明、复杂度、语言接口还是文档结构；
#. 修改题目正文及确实受影响的公共文件；
#. 使用针对性样例、编译、运行或静态检查验证修改；
#. 形成一个独立原子提交写入 ``main``；
#. 复查修复结果，并保持题号进度不受修复提交影响。

Git 使用方式
------------

日常对话工作采用直接 ``main`` 工作流。每轮对应一个完整提交，提交前后都读取最新状态。

当用户明确选择代码评审、多人协作或隔离实验时，本轮采用分支和 PR，并在用户指定的协作方式下
完成合并。

并发处理
--------

写入前重新读取 ``main``。当主分支在准备期间发生变化时，以新的状态重新计算本轮范围和目标文件，
再形成最终提交。这样状态文件始终对应实际进入 ``main`` 的内容。

完成判定
--------

一轮工作在以下条件同时满足时完成：

* 用户要求的范围已经处理；
* 正文、代码和证明通过对应质量检查；
* 相关索引与状态文件已经同步；
* 完整结果已经进入 ``main``；
* 提交后的复查结果与本轮报告一致。
