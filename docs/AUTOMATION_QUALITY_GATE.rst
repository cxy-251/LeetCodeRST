对话驱动质量门
==============

文件职责
--------

本文件定义普通生成、针对性抽查和历史题返工在写入 ``main`` 前必须完成的最低检查。质量门由当前对话中的
明确指令触发，不是后台任务。通过“单文件结构检查”只表示文件组织正确，不能代替教学内容质量验收。

规则入口
--------

检查优先级为：

#. ``state/PROGRESS.toml``；
#. ``state/REVIEW_INDEX.toml`` 的 active corrections；
#. 当前生效的前向规则；
#. 本文件和专项策略；
#. 历史归档。

``0151`` 起统一执行 ``docs/FORWARD_RULES_0151_ONWARD.rst``。每道公开题必须是唯一且自包含的 RST，
禁止用 ``.inc`` 或 ``.. include::`` 拆分题目正文和语言代码。

一、开始前检查
------------

#. 读取最新 ``main``、``AGENTS.md``、根 README 和 ``state/PROGRESS.toml``。
#. 确认当前处于新题生成、质量返工或针对性抽查阶段。
#. ``needs_revision`` 非空且新题生成被暂停时，只处理返工范围，不推进 ``next_problem``。
#. 读取 active corrections、当前前向规则和一篇同类型成熟题解。
#. 返工 0127 之后题目时，以 ``0001–0100`` 与 ``0128`` 为最低内容质量基线。
#. 只直接更新 ``main``，不创建分支、PR 或临时上传工作流。

二、教学内容质量基线
------------------

每道普通算法题必须根据实际教学需要包含以下内容。简单题可以合并相邻章节，核心信息不能消失：

#. **精确契约**：输入输出、长度和值域、字符域、结构前提、返回顺序、输入是否允许修改和平台类型；
#. **自建示例**：至少一个正常示例；存在典型错误路径时增加可区分反例；
#. **问题抽象**：把题目转化为真实算法模型，不直接从题面跳到代码；
#. **解法选择**：比较真正存在教学差异的方法，并说明主解法取舍；
#. **状态与不变量**：状态名称直接对应代码变量、递归参数、容器或数组槽位；
#. **完整正确性证明**：按题型覆盖合法性、完整性、无重复、排除安全性、最优性和终止性；
#. **真实复杂度**：区分核心状态、递归栈、输入物化、标准库调用、输出载荷、最坏/期望/摊还界；
#. **十语言实现**：固定顺序，代码与正文状态一致；语言特化算法必须独立解释、证明和计复杂度；
#. **验证证据**：准确区分实际运行、编译、静态检查、基准对拍和 sanitizer；
#. **关键边界与易错点**：优先给出可构造反例或真实失败路径；
#. **学习链**：新增知识、强化知识、强关联题目、自检问题与答案要点。

只有“算法、正确性、复杂度、十语言代码、三个问题”的摘要骨架，不得判定为合格题解。
章节数量不是目标；信息完整、推导可复用、读者能据此理解和复现算法才是目标。

三、题目契约与接口检查
--------------------

#. 文件名、题号、难度、原题链接和访问状态一致。
#. 公开函数名、参数、返回类型和平台接口准确。
#. ``ListNode``、``TreeNode``、``Node`` 等平台类型不在每题重复定义。
#. Julia 与 R 复用仓库统一节点表示，只解释当前题新增差异。
#. 原地接口分别说明调用者可观察修改、返回值和所有权。
#. 字符串题明确字节、UTF-16 代码单元、码点或字形簇单位。
#. 标准库 API 写明必要版本；C++ 默认不得无说明使用 C++20 API。

四、状态、证明与复杂度检查
------------------------

#. 状态定义能够逐项映射到实际代码。
#. 循环、递归、搜索、回溯、滑动窗口、双指针和动态规划写出核心不变量。
#. 使用强输入前提降低复杂度时，证明该前提删除了哪些候选或检查。
#. 多阶段算法分别证明阶段产物和阶段接口。
#. 不同语言采用不同算法时，不得共用一段模糊证明。
#. 正确性不能只写“遍历全部所以正确”，必须说明为什么不遗漏、不重复、不会错误排除并且终止。
#. 复杂度必须与实际实现一致，包含哈希期望界、队列/栈峰值、字符串构造、复制、所有权和适配器成本。

五、十语言检查
------------

固定顺序为 C、C++、Python、Java、Rust、Go、TypeScript、C#、Julia、R。

每个代码块检查：

#. 必要导入、辅助函数和平台签名；
#. 数值宽度、容量乘加和边界运算；
#. 输入修改、返回结构和失败路径；
#. 字符单位、索引转换、所有权和可变对象共享；
#. 结果快照是否独立；
#. 标准库语义与最低版本；
#. 代码中的主算法是否与正文证明一致。

六、单文件结构检查
----------------

#. 每道公开题在 ``problems/`` 中只对应一个 ``<题号>-<slug>.rst``。
#. 题目正文、证明、验证和十语言代码全部直接写在该 RST 中。
#. 题目 RST 中不得出现 ``.. include::``。
#. 当前题号和 slug 不得存在 ``.inc`` 或其他正文分片。
#. Premium 题只登记状态，不生成猜测性 RST。

结构通过但教学质量未通过时，该题仍保留在 ``needs_revision`` 中。

七、默认验证
----------

普通题默认执行：

#. 人工核对题目契约、状态、证明和代码映射；
#. 运行官方示例与 2 至 4 个关键边界；
#. Python 主实现实际运行；
#. C++ 主实现使用目标标准和严格警告编译，必要时运行；
#. C 涉及分配、指针、宽整数或所有权时严格编译并运行；
#. 其余语言检查接口、索引、容器、所有权和明显语法问题；
#. 高风险状态增加独立基准对拍、穷举、属性测试或 sanitizer。

不得把一种语言的通过外推为十语言全部运行通过。验证段必须与实际执行范围一致。

八、返工专项检查
--------------

返工题在普通检查基础上增加：

#. 与一篇前 100 题同类型成熟题解或 0128 逐项对照；
#. 不能只补标题，正文必须真正增加推导、证明和语言差异；
#. 原代码不能默认保留，重新检查平台类型、接口、版本和算法一致性；
#. 删除重复平台节点定义和未经说明的语言特化算法；
#. 完成题数、Premium 状态和 ``next_problem`` 保持不变；
#. 仅在全部验收项通过后从 ``needs_revision`` 删除题号。

九、RST、索引与状态检查
---------------------

#. 标题层级、代码块语言、相对链接和行宽正确。
#. 题号、难度、函数签名、正文方案和代码一致。
#. 当前范围 README 与根 README 同步返工进度。
#. ``state/PROGRESS.toml`` 准确记录已修复、剩余范围和下一批。
#. 搜索当前题，确认 ``.. include::`` 和题目 ``.inc`` 数量均为零。
#. 不提交日志、缓存、marker、未引用草稿或一次性分析报告。

十、提交检查
----------

#. 写入前重新读取最新 ``main``；主分支变化时重新计算目标树。
#. 多文件变化通过 Git blob、tree、单父 commit 和 ref 构造一个原子提交。
#. 使用非强制 fast-forward 更新 ``main``。
#. 禁止创建分支、PR、上传分片分支或临时组装工作流。
#. 提交后比较父提交与新提交，核对文件范围、状态和下一步。
#. 对话报告必须与 ``main`` 的实际提交、文件数和验证范围一致。

完成判定
--------

题目只有在内容质量、十语言实现、验证证据、唯一自包含 RST、索引和状态全部一致，并通过非强制
fast-forward 写入 ``main`` 后才算完成。单文件结构正确但教学内容低于基线时，仍属于待返工题。
