对话批次质量门
==============

文件定位
--------

本文件用于生成与阶段审查的验收。``0101–0150`` 的技术基线是
``docs/FORWARD_RULES_0101_0150.rst``，产物清理执行 ``docs/ARTIFACT_LIFECYCLE_POLICY.rst``。

当前阶段
--------

``state/PROGRESS.toml`` 当前为 ``review_ready``。``0101–0150`` 已完成，下一批审查 ``0101–0105``；
审查、规则归并和清理完成前不生成 ``0151``。

开始前
------

每轮读取 ``AGENTS.md``、根 README、``PROGRESS``、``REVIEW_INDEX``、当前规则、审查政策、生命周期规则、
知识账本以及本批五题的完整 RST。归档只在追溯规则来源或修复历史题时读取。

阶段审查门
----------

每道题完整检查：

#. 题目契约是否支撑所有代码假设；
#. 算法状态、转移、终止条件和证明是否与实现一致；
#. 十语言函数签名、平台类型、输入修改和返回所有权是否闭合；
#. 时间复杂度是否计入标准库、物化、输出载荷和峰值空间；
#. Rust 所有权、TypeScript 安全整数、Julia 一基索引、R 绑定与复制等语言语义是否准确；
#. 验证描述是否区分运行、编译、静态检查和基准对拍；
#. 关联链接、题号、文件名、知识账本和状态是否同步。

审查结果分为：稳定正向模式、确定性问题、语言高风险点、验证限制和前向规则候选。历史题默认不修改。

生成质量门
----------

进入下一生成阶段后，每题必须具有原创重述、区分性示例、算法状态、正确性证明、完整复杂度、十语言实现、
边界与易错点、知识更新、关联题目和验证证据。用户指定大范围时仍以质量优先，不能提交半成品。

验证证据
--------

``运行验证``
   执行正常、边界、随机或穷举用例。

``编译验证``
   通过编译器、严格警告或类型检查，不代表算法已经运行正确。

``静态验证``
   检查接口、索引、作用域、所有权、复杂度或逻辑，但未执行目标代码。

``基准对拍``
   与独立、明显正确的基准比较，基准不复用被测算法核心逻辑。

本批 ``0101–0150`` 已完成 Python 语法解析，C/C++ 严格编译，Java/Go 编译和 TypeScript 严格类型检查；
Rust、C#、Julia、R 为静态验证。阶段审查不能把这些证据夸大为全部语言运行通过。

产物清理门
----------

提交前确认：

#. 没有 marker、草稿、日志、缓存或未引用报告；
#. 活动 review 文件只属于尚未归并的当前审查；
#. 完成规则归并后，批次状态和 findings 立即归档并登记 manifest；
#. `AGENTS`、README、``PROGRESS``、``REVIEW_INDEX`` 和策略路径同步；
#. 活动目录不存在指向已删除路径的引用。

提交与复查
----------

一轮全部文件形成一个原子提交进入 ``main``。提交后复查完成范围、``review.current`` 或 ``next_problem``、
两个 README、知识账本、活动中间文件数量以及抽样题目的十语言代码块。
