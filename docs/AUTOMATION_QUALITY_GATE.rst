自动化批次质量门
================

适用范围
--------

本规则约束无人值守批次和手动多题批次。仓库当前可能处于两种阶段：

``review_extracting_rules``
   逐题读取 ``0001`` 至 ``0050`` 的 RST，只提炼后续规则，不修改历史题目，也不生成 0051。

``lessons_started``
   从 ``next_problem`` 继续生成新题，完整执行已经提炼出的质量门。

阶段判断以 ``state/PROGRESS.toml`` 为准。

必读文件
--------

每次开始前读取：

#. ``AGENTS.md``；
#. ``README.rst``；
#. ``docs/PROJECT_VISION.rst``；
#. ``docs/LANGUAGE_SCOPE.rst``；
#. ``docs/SOLUTION_AND_TYPES_POLICY.rst``；
#. ``docs/CONTENT_LANGUAGE_POLICY.rst``；
#. ``docs/RST_STYLE_GUIDE.rst``；
#. ``docs/RELATED_PROBLEMS_POLICY.rst``；
#. ``docs/REVIEW_AND_PREVENTION_POLICY.rst``；
#. ``docs/REVIEW_FINDINGS_0001_0050.rst``；
#. 本文件；
#. ``docs/AUTOMATION_DIRECT_MAIN_POLICY.rst``；
#. ``state/PROGRESS.toml``、``state/REVIEW_0001_0050.toml`` 和
   ``state/CONCEPT_LEDGER.toml``；
#. 最近至少 5 道相关题目的完整 RST。

PR 描述、提交信息和自动任务报告只能用于确认流程，不能代替读取题目正文。

规则提炼审查阶段
----------------

当 ``phase = "review_extracting_rules"`` 或
``next_batch.status = "blocked_by_review_extraction"`` 时：

* 从 ``review.current`` 开始按题号完整读取 RST；
* 默认每批审查 5 道，题目复杂时可以缩小；
* 每题结论写入 ``state/REVIEW_0001_0050.toml``；
* 跨题模式写入 ``docs/REVIEW_FINDINGS_0001_0050.rst``；
* 可以更新公共模板、质量门、语言规则和知识分类；
* 禁止修改 ``problems/0001-0100/0001`` 至 ``0050`` 的题目 RST；
* 禁止创建历史修复 PR；
* 禁止生成 0051 或推进 ``next_problem``；
* 即使发现旧题确定性问题，也只记录风险和前向规则，除非用户明确要求修改该题。

审查证据必须来自完整正文，不能从 PR 标题或完成报告推断。

新题批次范围
------------

只有规则提炼审查完成、``next_batch.status = "ready"`` 后，才允许生成新题。

一轮从 ``next_problem`` 开始，按难度预算连续处理 1 至 3 道题：

* Easy = 1；
* Medium = 2；
* Hard = 4；
* 目标总分 4 至 6；
* 加入下一题会超过 6 时结束；
* 同批禁止两道 Hard；
* 连续三道 Easy 可以 3 分结束。

质量优先于题量。尾部题未达到质量门时删除半成品，只提交连续且完整的前缀。

题意与约束质量
--------------

新题必须明确：

* 输入、输出、结果顺序和是否允许修改输入；
* 数值范围、长度下界、字符集合和平台类型；
* 哪些约束用于证明整数不会溢出、索引不会越界或字符可按字节处理；
* 至少一个正常示例；
* 当前算法容易出错时，增加能区分正确与错误实现的边界示例。

禁止使用“常见测试字符”“通常不会溢出”“一般非空”等模糊假设替代题目约束。

字符串字符模型
--------------

字符串题在写代码前必须定义算法使用的字符单位：

* 字节；
* UTF-16 代码单元；
* Unicode 码点；
* 字形簇。

十种语言使用不同单位时，必须由题目精确字符约束证明它们在本题等价。若题目允许非 ASCII
字符，不能把字节实现、UTF-16 实现和码点实现统称为同一语义。

任何按字节重排后重新构造字符串的实现，都必须证明不会拆散多字节编码。不能只写
“题目字符范围允许”，必须列出具体字符集合或平台约束。

教学密度与解释衰减
------------------

一个核心公式、边界推导或正确性证明只保留一个完整主讲位置：

* “思路”负责建立模型；
* “正确性依据”负责证明，而不是再次重述步骤；
* “易错点”给反例或错误写法；
* “强化知识”只说明与历史知识的差异；
* “自检”要求读者重新推导，不复制正文结论。

相邻题复现同一知识时，只完整解释新增状态、新边界或新语言语义。禁止为了增加篇幅在题目重述、
问题抽象、证明、易错点和答案要点中重复同一段推导。

算法与证明质量
--------------

正确性依据不能只复述代码。根据算法类型证明实际决策：

* 状态或不变量为什么成立；
* 指针移动、候选排除或剪枝为什么安全；
* 搜索是否完整、是否重复、是否终止；
* 贪心局部选择为什么不损失最优解；
* 回溯如何覆盖搜索空间并去重；
* 动态规划状态是否充分，转移是否无遗漏；
* 二分查找的搜索区间、单调方向、排除安全性、答案存在性和终止性；
* 讲解与十种语言代码是否使用同一个算法。

递归解法还必须：

* 写出最坏递归深度；
* 将深度与题目最大输入规模对应；
* 检查 Python、R、JavaScript、JVM、CLR 等目标环境的实际栈风险；
* 无法证明安全时改为迭代、显式栈或自底向上动态规划。

复杂度质量
----------

复杂度必须：

* 定义 ``n``、``m``、``k``、``U``、数字位数 ``d`` 等变量；
* 区分最坏、平均、期望和摊还复杂度；
* 哈希表方案同时说明期望与最坏情况；
* 区分算法额外空间、输入规范化空间、递归栈和返回结果空间；
* 计入排序、哈希、重复扫描、字符串拼接和标准库调用；
* 计入 ``[]byte(s)``、``collect(s)``、``strsplit``、切片、重新编码和结果复制；
* 排列、组合、枚举、分组和字符串构造计入输出数量与复制成本；
* 十种语言存在不同渐进成本时，增加语言差异说明，不能用一条结论覆盖全部实现。

整数逐位算法优先使用数字位数 ``d``。需要对数表达时写 ``O(log(|x| + 1))``，或者明确限定
``x > 0``，不能把 ``x = 0`` 或负数留在符号定义域之外。

十语言完整性
------------

主解法覆盖 C、C++、Python、Java、Rust、Go、TypeScript、C#、Julia 和 R，并实现相同算法语义。

每种语言必须明确：

* 必要导入由代码直接给出，或明确声明由平台预置；
* 标准库符号使用其直接定义头文件、包或命名空间，禁止依赖传递性导入；
* 非平台辅助函数、比较器、哈希键和状态对象完整；
* 使用版本相关 API 时声明最低版本，或使用本地兼容实现；
* 输入是否被消费、移动、排序、交换或原地修改；
* 返回结构、结果顺序、资源所有权和释放责任；
* 固定宽度整数、索引、字符单位、作用域和所有权边界。

危险算术必须先扩宽操作数再计算。把最终结果转换到宽类型，不能修复已经在窄类型中发生的
溢出。幂、移位、取负、乘法和加法都检查转换顺序，例如使用 ``Int64(2)^31``，而不是
``Int64(2^31)``。

失败路径
--------

失败和不可达路径不能伪装成普通答案：

* C 分配失败不得返回部分链表、部分数组或部分组合结果；
* 已分配资源必须清理，或者明确声明平台保证分配成功并省略伪错误处理；
* 资源失败不得静默返回合法的 ``false``、``0``、空数组、空字符串或 ``0.0``；
* 使用断言、异常、错误返回、``unreachable`` 或明确的平台前提；
* 十种语言的失败契约应保持一致，不能一部分抛错、一部分静默返回合法值。

高风险语言检查
--------------

C
~

* 容量由上界证明或动态增长；
* 二维返回结构检查外层容量、每行容量、``returnSize`` 和 ``returnColumnSizes``；
* 检查失败清理、输入修改、返回所有权、无符号下溢和整数提升；
* ``INT_MIN``、乘法、加减和比较器运算在需要时先扩宽。

C++
~~~

* 区分 ``size_t`` 与有符号下标；循环下标、容器长度和差值使用一致且安全的类型；
* 差值和递减前证明不会下溢；
* 检查迭代器失效、引用生命周期、比较器严格弱序和输入原地修改；
* 每个标准库符号包含其直接定义头文件，例如 ``std::move`` 对应 ``<utility>``；
* 平台预置头文件必须显式声明。

Python
~~~~~~

* 切片和容器复制计入复杂度；
* 检查可变对象共享、闭包变量、递归深度和大整数与其他语言的差异。

Java 与 C#
~~~~~~~~~~

* 中间运算在运算前提升到宽类型；
* 检查集合键、装箱、字符单位、递归和切片/子串复制；
* 必要 ``import``、``using`` 或平台预置边界明确。

Rust
~~~~

* 代码必须通过真实借用检查；
* 检查 ``take``、``clone``、移动、借用生命周期和 ``Option``；
* 输入所有权被消费时明确说明；
* 为所有权复制整个结构时计入复杂度；
* 按字节重排后构造 ``String`` 时，用精确字符约束证明 UTF-8 仍有效。

Go
~~

* ``[]byte(s)`` 会复制字符串，必须计入空间；
* 检查切片底层数组共享、``append``、字节与码点语义；
* 使用 ``min``、``max`` 等版本相关 API 时声明 Go 版本或提供辅助函数；
* 检查 ``int`` 宽度和映射零值。

TypeScript / JavaScript
~~~~~~~~~~~~~~~~~~~~~~~

* ``number`` 安全整数范围；
* 位运算的 32 位有符号转换；
* ``Map.get`` 的 ``undefined`` 与合法零值；
* 字符串使用 UTF-16 代码单元；
* 使用 ``--strict``，类型检查与运行验证分开记录。

Julia
~~~~~

* 零基算法坐标与一基数组位置逐项转换；
* ``a:b`` 的递减范围和零长度切片显式守卫；
* ``collect`` 和普通切片产生副本，计入复杂度；
* 原地 ``!`` 接口、返回值、整数除法和抽象容器类型正确；
* 边界常量在目标宽类型中构造，避免先用宿主 ``Int`` 运算再转换。

R
~

* 当前递归层局部变量使用 ``<-``，跨层共享状态优先使用显式 ``environment``；
* ``<<-`` 只表示更新父作用域绑定，不证明矩阵或列表单元为常数时间原地修改；
* 记忆化和高频共享状态使用 ``environment``，或单独验证并计入写时复制成本；
* 可能为空的序列使用 ``seq_len``、``seq_along`` 或守卫；
* ``strsplit``、向量复制和写时复制计入复杂度；
* 一基索引、回收规则、值语义和原地接口明确。

验证证据
--------

最终报告必须区分：

``运行验证``
   已执行正常、边界、随机或穷举用例。

``编译验证``
   已通过编译器、严格警告或类型检查；不能据此宣称算法运行正确。

``静态验证``
   只检查接口、索引、作用域、所有权或逻辑。

``基准对拍``
   与独立、明显正确的基准比较，基准不能复用被测算法核心逻辑。

禁止把一种语言的运行结果外推为其余九种语言全部正确。

单题完成判定
------------

只有全部满足以下条件，新题才可计入完成范围：

#. 教学主线完整；
#. 十种语言主解法完整且语义一致；
#. 精确约束支撑代码假设；
#. 正确性证明覆盖算法决策；
#. 共享推导没有在多个章节机械重复；
#. 复杂度包含语言特有复制、递归深度和结果成本；
#. 导入、辅助函数、版本和平台前提明确；
#. 危险算术在运算前完成类型扩宽；
#. 失败路径不返回部分或伪合法结果；
#. 验证证据描述准确；
#. RST 结构、索引和知识账本同步。

Git 流程
--------

规则提炼审查和正常内容批次都使用一个分支、一个非 Draft PR，并在质量门通过后 squash merge。

自动内容批次遵守 ``docs/AUTOMATION_DIRECT_MAIN_POLICY.rst``，只使用
``automation/leetcode-current``。合并前重新读取最新 ``main``，合并后确认题目、索引、状态和
PR ``merged=true``。

规则提炼审查 PR 只能修改公共规则、审查记录和状态文件，禁止包含历史题目 RST。
