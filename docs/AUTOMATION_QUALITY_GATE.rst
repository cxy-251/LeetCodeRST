自动化批次质量门
================

适用范围
--------

本规则专门约束定时任务和无人值守批次。自动任务可以在一轮中处理连续多题，但每道题都必须
独立达到完整教学质量，不能因难度预算、运行频率或批次题量压缩教学主线。无法完成完整题目时，
不得把半成品登记为已完成。

基准文件
--------

每次开始前必须读取：

#. ``AGENTS.md``；
#. ``docs/PROJECT_VISION.rst``；
#. ``docs/LANGUAGE_SCOPE.rst``；
#. ``docs/SOLUTION_AND_TYPES_POLICY.rst``；
#. ``docs/CONTENT_LANGUAGE_POLICY.rst``；
#. ``docs/RST_STYLE_GUIDE.rst``；
#. ``docs/RELATED_PROBLEMS_POLICY.rst``；
#. 本文件；
#. ``docs/AUTOMATION_DIRECT_MAIN_POLICY.rst``；
#. ``state/PROGRESS.toml`` 与 ``state/CONCEPT_LEDGER.toml``；
#. 最近至少 5 道已经进入 ``main`` 的完整题目。

0001 至 0007 是初始质量基准，最新已完成题目是当前直接基准。自动任务需要学习其教学密度、
论证方式、代码注释风格和多语言覆盖，不得只复用标题骨架。

批次范围
--------

一轮从 ``next_problem`` 开始，按 ``docs/AUTOMATION_DIRECT_MAIN_POLICY.rst`` 的难度预算连续处理
1 至 3 道题。禁止跳过中间可访问题目后继续更大题号。

每道题完成后立即执行本质量门，再决定是否把下一题加入批次：

* 已完成题目必须先独立通过质量门；
* 批次尾部题目无法完成时，应删除该题的半成品并缩小批次；
* 已通过题目可以作为连续前缀提交，不必因尾部题失败而全部作废；
* Premium 或题意无法可靠确认时，只登记跳过或阻塞，不猜测题意。

必备教学主线
------------

每道普通算法题必须根据实际内容完整覆盖以下教学功能：

#. 标题与题目信息；
#. 原创题目重述，明确输入、输出和关键约束；
#. 至少一个自建正常示例，并在边界容易出错时增加边界示例；
#. 问题抽象，说明题目真正要求维护或计算的对象；
#. 解法选择，解释主解法与主要替代方法的复杂度和取舍；
#. 主解法的状态、变量含义、执行过程或核心不变量；
#. 独立的正确性依据，不能只把代码流程换一种说法；
#. 时间复杂度与空间复杂度，并说明复杂度中的变量含义；
#. 10 种核心语言的完整主解法；
#. 各语言真正需要提醒的接口、数值、索引、内存、所有权或字符语义；
#. 易错点与关键边界；
#. 本题新增或强化的知识；
#. 最小自检问题与答案要点；
#. 只有存在强关联时才写关联题目，通常 1 至 3 个，最多 5 个。

章节名称可以随题目调整，教学功能不得被静默删除。简单题可以减少重复背景，不能省略
问题抽象、核心不变量或状态、正确性、复杂度、关键边界、多语言实现和自检。

多语言质量
----------

每道题的主解法必须覆盖 C、C++、Python、Java、Rust、Go、TypeScript、C#、Julia 和 R。
代码需要符合各语言接口习惯，并特别检查：

* C 的缓冲区、内存所有权、整数范围和返回接口；
* C++ 标准库调用、迭代器和整数转换；
* Python 的整数与切片语义；
* Java、TypeScript 与 C# 的固定宽度整数及溢出；
* Rust 的所有权、转换和 ``Option`` / ``Result`` 边界；
* Go 的切片、字符串与数值转换；
* Julia 和 R 的一基索引、数值类型与平台接口差异。

不得为了缩短篇幅去掉中文教学注释。已经进入 ``familiar`` 的普通语法可以衰减，当前
算法的状态变化、关键分支、溢出风险、索引换算和 API 陷阱仍需解释。

单题完成判定
------------

只有全部满足以下条件，某一道题才能计入本轮完成范围：

#. RST 教学主线完整；
#. 10 种语言均有完整主解法；
#. 代码与讲解采用同一算法；
#. 正确性和复杂度能够独立阅读；
#. RST 标题、指令、缩进、链接和代码块无明显结构错误；
#. 题目相关知识账本条目已经准备；
#. 与最近题目对照后不存在明显的骨架化或教学密度骤降。

禁止用文件行数作为唯一质量指标，也禁止以“题目简单”为理由只留下定义、代码和一句
复杂度。发现质量不足时继续完善当前题，或从批次尾部移除该题；不得保留半成品后继续下一题。

批次完成判定
------------

只有全部满足以下条件，才能更新 ``completed_count`` 和 ``next_problem``：

#. 所有提交题目均逐题通过质量门；
#. 题号从原 ``next_problem`` 开始连续；
#. 题数为 1 至 3，难度预算符合固定分支策略；
#. 所有题目文件、范围索引、根 README、进度和知识账本同步；
#. ``next_problem`` 指向批次末题之后的第一个未处理题号；
#. PR 中不存在批次外题目、半成品或自动化规则修改。

自动 Git 流程
------------

自动任务必须遵守 ``docs/AUTOMATION_DIRECT_MAIN_POLICY.rst`` 中的固定分支批次策略：

#. 永远只使用 ``automation/leetcode-current``；
#. 禁止创建题号分支、时间戳分支和 finalize 分支；
#. 每轮提交 1 至 3 道连续完整题目及其索引、进度和知识账本；
#. 所有内容组成一个提交和一个非 Draft PR；
#. 逐题质量门和批次一致性全部通过后 squash merge；
#. 合并后重新读取 ``main``，确认题目文件存在且 ``next_problem`` 正确推进；
#. 未成功合并、主分支未推进或质量不确定时必须报告失败；
#. 同一时刻存在未关闭自动化 PR 时不得创建第二个 PR。
