项目愿景与教学设计
==================

为什么按题号顺序推进
--------------------

本项目不按数组、链表、树、动态规划等专题集中刷题，而是按照 LeetCode 编号顺序推进。编号顺序会让不同主题交错出现，这种交错学习能够持续唤醒旧知识，避免长时间只学习一个专题后遗忘前面的内容。

题号顺序是默认主线。专题索引可以作为辅助导航存在，不能替代主线顺序。

教学资源如何分配
----------------

文档不追求每题同样长，也不追求每个知识点都解释。有限的篇幅优先投入到以下内容：

* 当前题目的核心抽象；
* 决定算法正确性的状态、不变量和证明；
* 容易写错的边界；
* 首次出现或仍不稳定的语言知识；
* 与以前题目不同的新结构；
* 需要周期复习的疑难算法。

高频基础语法的解释会逐渐减少。复杂算法、证明和状态设计会在后续题目中再次出现时重新解释。

知识点的两种记忆策略
--------------------

语法与常用库
~~~~~~~~~~~~

语法、容器和常用标准库通常会在相邻题目中反复出现。它们采用解释衰减：

#. 首次出现时完整解释；
#. 接下来一到数次保留短提醒；
#. 熟悉后正常使用，不再制造重复注释；
#. 长时间未出现或出现新边界时重新提醒。

疑难算法与证明
~~~~~~~~~~~~~~

复杂算法不采用快速衰减。动态规划、单调结构、图算法、字符串算法、高级数据结构、数学推导等内容需要周期性复现。

每次复现重点回答：

* 这次状态如何定义；
* 转移或操作为什么成立；
* 与以前题目的结构有什么相同和不同；
* 哪些直觉容易误导；
* 如何验证实现没有破坏不变量。

多语言学习目标
--------------

本项目长期目标是覆盖 LeetCode 支持的主要语言。语言覆盖采用渐进方式，避免一次性生成大量未经验证的机械翻译。

同一算法在不同语言中，应展示语言自身的重要差异，例如：

* Python 的数据模型、容器协议和迭代方式；
* C++ 的引用、迭代器、值语义、资源管理和标准库；
* Rust 的所有权、借用、模式匹配和迭代器；
* Go 的切片、map、零值和多返回值；
* Java 的泛型、集合、装箱和比较语义；
* TypeScript 的类型系统、Map、数组和类型收窄；
* C 的指针、数组边界和手工内存管理；
* 其他语言各自真正影响实现方式的机制。

代码注释不能只是把代码翻译成中文。

单题文档的内容边界
------------------

每道题使用原创重述，不复制 LeetCode 的完整题干、官方题解、Premium 内容或测试数据。

单题文档应该包含足够信息帮助读者理解和复现算法，包括：

* 题号、题名、难度、标签和原题链接；
* 原创问题重述；
* 自建示例；
* 问题抽象；
* 解法与正确性依据；
* 时间和空间复杂度；
* 多语言实现；
* 易错点；
* 新增与强化知识；
* 最小自检；
* 与历史题目的关联。

简单题可以省略低价值章节。复杂题可以增加状态表、流程、证明、反例和多个有意义的解法。

Premium 题目
------------

助手不能绕过付费墙。题目不可访问时，只登记题号和状态，然后继续后续公开题目。

后续可以补写的合法来源包括：

* 用户主动提供的题目信息；
* 用户自己的代码和笔记；
* 题目后来转为公开；
* 足以确认接口和要求的公开官方信息。

无法确认时不猜测。

RST 作为正式载体
-----------------

RST 适合本项目的长期维护：

* ``.. code-block::`` 展示多语言代码；
* ``.. note::`` 和 ``.. warning::`` 表达边界；
* ``.. list-table::`` 对比复杂度和语言差异；
* ``:doc:`` 建立题目之间的关联；
* Sphinx 可以构建 HTML、PDF 和 EPUB；
* 标准化指令便于后续自动检查。

项目会在样板题稳定后补充 Sphinx 构建、代码验证和连续编号检查。

跨对话接手
----------

任何新的 ChatGPT 对话或其他助手都不应依赖上一段对话的隐含记忆。接手所需信息必须落在仓库中：

* ``AGENTS.md`` 保存执行规则；
* ``state/PROGRESS.toml`` 保存推进位置；
* ``state/CONCEPT_LEDGER.toml`` 保存知识教学状态；
* 最近题目展示当前写作和注释密度；
* PR 正文保存当前批次结果与遗留事项。

只要这些文件持续更新，任务就能在不同对话之间稳定传递。
